# 춘천과팅 운영 확인표

작성일: 2026-09-25. 이 문서는 운영자가 완료해야 할 절차와 남은 결정을 기록한다. 문서 작성만으로 설정 변경, 관리자 인증 등록, 실서비스 백업이 완료된 것은 아니다. 실제 이름·학생증·접속 토큰·비밀 키는 이 저장소에 기록하지 않는다.

## 현재 확인된 범위

- 격리된 PostgreSQL 17에서 권한·동시 처리·마이그레이션 반복 적용과 합성 데이터 복원을 검증했다.
- 실제 로컬 Supabase에서 가입, 학생증 파일 업로드, 관리자 승인, TOTP 추가 인증, 팀 등록, 매칭, 파일 삭제 후 탈퇴 처리를 검증했다. [검증 범위와 보고서](validation/README.md)를 참고한다.
- 운영 관리자에게 검증 완료된 MFA 수단은 확인 시점에 0개였다. 기능 구현 완료와 실제 계정 보호 완료를 구분한다.
- 운영 데이터의 독립 백업 보관처, 담당자, 복구 목표, 실제 복구 훈련은 아직 지정·검증되지 않았다.
- 유출 비밀번호 차단은 현재 비활성 상태다. Supabase의 해당 기능은 Pro 이상에서 제공된다. 결제나 요금제 변경은 별도 결정 사항이다. [공식 비밀번호 보안 안내](https://supabase.com/docs/guides/auth/password-security)

## 1. 관리자 추가 인증 등록

담당: 서비스 관리자 본인. 완료 증거에는 날짜와 성공 여부만 남기고 QR 코드·수동 등록 키·일회용 코드는 남기지 않는다.

- [ ] 관리자 비밀번호를 다른 서비스와 겹치지 않게 관리하고, 등록 전 인증 앱의 안전한 백업 방법을 정한다.
- [ ] 배포된 사이트에서 로그인한 뒤 **관리자 메뉴 → 계정 보안**, 또는 [관리자 계정 보안](https://chuncheon-dating5-0.vercel.app/admin/security)을 연다.
- [ ] **인증 앱 연결**을 누르고 본인 인증 앱에서 QR 코드를 스캔한다. 필요한 경우 화면의 수동 등록 키를 사용한다.
- [ ] 앱의 6자리 코드를 입력하고 **인증하기**를 누른다. 화면에 **2단계 인증 사용 중**과 **이 기기에서 추가 인증이 완료되었습니다**가 표시되는지 확인한다.
- [ ] 별도 기기 또는 새 비공개 창에서 다시 로그인한다. 코드 입력 전 관리자 정보가 열리지 않고, 올바른 코드 입력 후 정상 접근되는지 확인한다. 기존 다른 기기의 재로그인이 필요할 수 있다.
- [ ] 독립된 기기·안전한 보관처에 예비 인증 수단을 준비하고 작동을 확인한다. 이 서비스는 복구 코드 발급 화면을 제공하지 않는다.
- [ ] GitHub, Vercel, Supabase **플랫폼 계정**의 추가 인증도 별도로 점검한다. 서비스의 `/admin/security` 등록이 플랫폼 계정까지 보호하지는 않는다.

현재 정책은 선택 등록 방식이다. 검증된 인증 수단이 있는 관리자만 추가 인증을 완료한 세션으로 관리자 권한을 사용할 수 있다. 마지막 인증 수단을 해제하면 이 보호도 해제된다. [Supabase의 선택 등록 MFA 설명](https://supabase.com/docs/guides/auth/auth-mfa)

### 인증 기기를 잃어버렸을 때

1. 예비 인증 수단이 있다면 그것으로 로그인하고, `/admin/security`에서 분실한 수단을 해제한 뒤 새 수단을 등록한다.
2. 모든 수단을 잃었다면 사전에 지정한 프로젝트 소유자에게 별도 연락 채널로 복구를 요청한다. 요청자의 신원을 확인하고 처리 담당자·사유·시각을 기록한다. 이름·학교·학번을 알고 있다는 이유만으로 관리자 인증을 해제하지 않는다.
3. 프로젝트 소유자가 Supabase 관리 권한으로 해당 앱 사용자의 인증 수단을 확인하고 분실 수단만 해제한다. 콘솔에서 해당 기능을 제공하지 않는 경우, 승인된 서버 환경의 Auth Admin `mfa.deleteFactor` 절차를 사용한다. 서비스 키를 브라우저·저장소·메신저에 붙여 넣지 않는다. 검증된 수단 삭제는 해당 사용자의 활성 세션을 종료한다. [공식 관리자 복구 API](https://supabase.com/docs/reference/javascript/auth-admin-deletefactor)
4. 계정 탈취가 의심되면 비밀번호 재설정과 세션 정리를 함께 진행한다. 마지막 수단 삭제 후에는 추가 인증 보호가 없는 구간이 생기므로 즉시 새 수단을 등록하고 새 로그인으로 접근 제한을 재확인한다. 데이터베이스의 관리자 검사 함수를 약화시키는 방식으로 우회하지 않는다.
5. Supabase 플랫폼 계정 자체의 인증 수단 분실은 위 앱 사용자 복구와 다르다. 플랫폼 계정에도 예비 수단을 미리 확보한다. [플랫폼 계정 MFA 및 복구 제한](https://supabase.com/docs/guides/platform/multi-factor-authentication)

복구 책임자: **미정** / 대체 책임자: **미정** / 안전한 연락 경로: **미정** / 마지막 복구 연습: **미실시**.

## 2. 백업 운영 결정

아래 항목을 실제 값으로 확정하고 실행해야 한다. 비밀 자체 대신 접근 권한을 관리하는 보관처의 이름만 기록한다.

| 결정 항목 | 현재 상태 | 완료 기준 |
| --- | --- | --- |
| 백업·복구 책임자와 대체 담당자 | 미정 | 두 사람이 절차와 비상 접근 방법을 확인 |
| 허용 가능한 데이터 손실 시간(RPO) | 미정 | DB와 파일 각각의 목표 및 백업 주기 결정 |
| 허용 가능한 서비스 중단 시간(RTO) | 미정 | 장애 발견부터 검증 후 재개까지 목표 결정 |
| 독립 백업 보관처 | 미정 | 원본 프로젝트·개발 PC 장애와 분리된 비공개 저장소 |
| 암호화와 복호화 키 보관 | 미정 | 암호화된 백업과 분리된 키, 최소 권한, 복구 담당자 접근 확인 |
| 보관 기간·세대 수·자동 만료 | 미정 | 개인정보 처리방침과 일치하는 DB·파일·로그 보관 기간 |
| 실패 알림 수신자와 대응 시간 | 미정 | 실패·누락·복구 불가능 알림을 실제 수신 확인 |
| 복원 훈련 주기와 다음 실시일 | 미정 | 정기 일정 및 주요 변경 후 추가 검증 책임 결정 |
| 비용 한도와 요금제 | 미정 | 승인된 예산 안에서 선택; 유료 기능 자동 신청 금지 |

Free 프로젝트에는 정기적인 외부 내보내기와 별도 보관이 권장된다. Pro 자동 DB 백업의 기본 보관 기간은 7일이며, **DB 백업은 Storage 파일의 실제 내용을 포함하지 않는다**. 프로젝트와 함께 사라지는 내부 백업만으로 독립 복구를 충족하지 않는다. [Supabase 백업 범위와 보관 기간](https://supabase.com/docs/guides/platform/backups)

### 첫 백업 및 복원 훈련의 완료 기준

- [ ] 운영자가 승인한 대상·주기·암호화 보관처를 확정한 뒤 DB를 내보낸다. 애플리케이션 테이블뿐 아니라 필요한 Auth/Storage 메타데이터, 함수, 정책, 트리거, 권한, 역할과 복원에 필요한 설정의 포함 범위를 확인한다. 내보내기 명령 하나로 모든 범위가 포함된다고 가정하지 않는다.
- [ ] 학생증 Storage 파일을 별도로 암호화하여 보관한다. 경로·파일 수·크기·내용 해시와 백업 시각을 보호된 목록으로 기록한다. 파일과 DB의 백업 시각 차이 및 삭제 처리 중 충돌을 다루는 절차를 정한다.
- [ ] 암호화 파일을 내려받아 복호화할 수 있는지 확인한다. 비밀번호·토큰을 CI 로그, 공개 아티팩트, 이 저장소에 올리지 않는다.
- [ ] 승인된 격리 환경에 복원한다. 메일·외부 알림·운영 연결을 차단하고 복원본에도 운영 데이터와 같은 접근 제한을 적용한다. 훈련 때문에 운영 프로젝트를 덮어쓰지 않는다.
- [ ] 테이블별 수·내용, 함수·정책·역할·권한, 파일 수·해시를 대조한다. 승인된 검증 계정으로 가입/로그인, 관리자 추가 인증, 학생증 접근 제한, 팀/매칭, 탈퇴 흐름을 확인한다.
- [ ] 백업 이후 누락되는 변경을 계산해 실제 RPO를 기록하고, 장애 선언부터 환경 준비·복원·파일 복원·권한 검증·재개 판단까지 걸린 전체 시간을 RTO로 기록한다.
- [ ] 탈퇴 처리된 개인정보가 예전 백업 복원으로 다시 서비스에 노출되지 않도록 복원 후 삭제 내역 반영 절차를 검증한다. 보관 기간이 끝난 백업·파일·훈련 복사본을 정리하고 처리 기록을 남긴다.

### 이번 로컬 검증의 한계

합성 데이터 복원은 12개 확인 항목과 16개 연결의 640회 처리에서 통과했다. DB 내용·권한 복원과 동시 수정의 일관성을 증명하지만, 운영 백업을 실제로 확보했다는 의미는 아니다. 측정된 약 0.87초는 작은 로컬 DB의 복원·검증 시간이며 운영 RTO가 아니다. 백업 후 의도적으로 쓴 1개 행은 복원되지 않아 스냅샷 이후 변경 손실도 확인했다.

CLI 2.117.0이 선택한 로컬 Postgres/Auth/Storage 등의 컨테이너 이미지는 합성 계정 통합 시험에 사용했다. **컨테이너 이미지 캐시에는 운영 DB·학생증 파일·프로젝트 설정의 백업이 없다.** 이미지 재다운로드나 서비스 재시작만으로 운영 데이터를 복원할 수 없다. 로컬 시험 후 해당 시험의 컨테이너와 데이터 볼륨은 정리했으며 이미지 캐시만 남겼다. 운영과 로컬 백엔드 버전 차이, 서비스 설정, 키, 파일 내용은 별도 복원 검증 대상이다.

## 3. 계정 찾기와 탈퇴 정책의 합치

담당: 서비스 운영자 및 개인정보 정책 검토 담당자. 문구를 바꾸는 것만으로 실제 파기 절차가 생기지는 않는다. 아래 결정은 아직 완료되지 않았다.

- [ ] **아이디 찾기:** 현재는 이름·학교와 학번 또는 연락처가 일치하면 아이디를 반환한다. 이 정보의 지식이 해당 계정의 소유권을 증명하지는 않는다. 타인의 공개 정보를 이용한 조회 위험, 반환 범위, 시도 제한, 문의 절차를 검토한다.
- [ ] **비밀번호 재설정:** 현재 요청은 관리자에게 전달된다. 등록된 연락 수단 등을 통한 소유권 확인과 처리 기록을 정하고, 요청의 이름·학교만으로 비밀번호를 재설정하지 않는다. 임시 비밀번호·문의 내용의 전달과 보관 기준도 정한다.
- [ ] **탈퇴 접수와 승인:** 현재 탈퇴 요청 즉시 서비스 이용을 중단하고 팀을 삭제한다. 이름·연락처·학번·학생증은 관리자 확인 단계에서 정리한다. 접수부터 승인까지 처리 기한과 대체 담당자를 정한다.
- [ ] **남는 데이터:** 승인 후에도 Auth 계정과 아이디, 프로필의 학교·성별·동의/인증 기록 등은 남는다. Auth의 이름 메타데이터만 제거하며 신고 등 별도 보관 대상도 목록화해야 한다. 이는 인증 계정 전체 삭제가 아니다. 이전 토큰의 메타데이터는 만료·갱신 전까지 남을 수 있다.
- [ ] **문구와 구현의 차이:** 현재 동의 약관에는 탈퇴 시 지체 없는 파기, 공개 삭제 안내에는 아이디만 최대 1년 보관한다는 내용이 있다. 현재 구현에 1년 후 자동 파기 절차는 없다. 보관 목적·항목·기간·정기 파기 작업과 재가입 제한을 먼저 확정하고 안내/약관/구현을 일치시킨다.
- [ ] 정식 약관 변경이 필요하면 한국어 원문과 번역본, 고지·재동의 계획, `TERMS_VERSION`, DB 동의 검증 버전을 함께 검토한다. 법적 적정성을 이 점검만으로 확정하지 않는다. 운영 Auth 계정이나 기존 데이터를 임의로 삭제하지 않는다.

## 4. 배포와 일상 대응

- [ ] `application`·`database` 필수 검증, main 강제 푸시·삭제 금지, 관리자 우회 제한이 실제 적용됐는지 저장소 설정에서 확인한다. 설정 예정과 적용 완료를 구분한다.
- [ ] 의존성 보안 업데이트와 알림 담당자를 지정하고, 보안 업데이트 PR도 동일한 검증을 거쳐 적용한다.
- [ ] 배포 후 읽기 전용 점검 결과를 확인하고 실패 시 대응할 담당자를 정한다. HTTP 정상 응답은 실제 사용자의 가입·결제 없는 운영 흐름 전체 성공을 의미하지 않는다.
- [ ] 가입 인증 대기, 탈퇴 승인 대기, 신고 처리, 로그인/업로드 오류를 정기적으로 점검하고 처리 지연 기준을 정한다. 로그에는 학생증 내용이나 비밀을 남기지 않는다.
- [ ] 실제 사용자 관찰에서 가입 완료율, 인증 대기 시간, 신청→수락 전환, 반복 이용, 도움 요청을 확인한다. 테스트 개수와 코드 개선만으로 이용 수요나 실제 만남의 성과를 입증하지 않는다.
