| 단계 | 가능한 기능 | 제한 |
|---|---|---|
| 학생증 없는 가입 | 기존 약관 동의·회원 정보 등록, 로그인, 승인된 상대 팀 둘러보기, 내 팀 초안 저장·수정·삭제 | 공개 팀 등록, 매칭 신청·수락 금지 |

| 관리자 승인 | 작성자가 '팀 공개하기'를 눌러 공개, 기존 방식으로 매칭 | 승인만으로 초안 자동 공개하지 않음 |
| 정지 / 탈퇴 | 기존 계정 차단 유지 | 탈퇴 시 초안과 초안 연락처 삭제 |

상대의 전화번호·카카오톡 ID는 현재 서비스처럼 일반 회원에게 직접 제공하지 않는다.
승인된 양 팀의 매칭 수락 이후 관리자가 기존 알림의 명단을 사용해 단체방을 개설한다.
새 연락처 공개 API는 추가하지 않는다. 자신의 연락처·자신의 초안은 본인이 관리할 수 있다.
성별·학교·아이디의 기존 변경 제한과 관리자 MFA는 유지한다.

## 구현 및 운영 영향

- 가입 화면의 학생증 업로드 의무 제거. 기존 사진 포함 가입 API도 계속 호환된다.
- /me/verification에서 사진 제출·거절 후 재제출. 원본 사진은 기존 private student-ids 버킷에 저장한다.
- 초안은 새 public.team_drafts 테이블에 회원당 하나만 저장한다. 기존 teams와 team_members에 넣지 않아 홈 목록·매칭·통계에 포함되지 않는다.
- 초안 테이블의 SELECT·DELETE는 활성 작성자에게만 허용한다. 직접 INSERT·UPDATE는 차단하고 서버 함수에서 소유권·동의·명단을 검증한다.
- save_my_team_draft: 계정 행 잠금으로 동시 저장을 직렬화하고 유효한 명단만 저장한다.
- publish_my_team_draft: 관리자 승인 확인 후 기존 save_my_team을 호출해 팀과 명단을 원자적으로 공개한다. 실패하면 초안을 보존한다.
- 기존 save_my_team의 승인 회원 저장 동작은 유지하고, 성공 시 본인의 남은 초안만 제거한다. 이전 배포의 직접 팀 작성 경로도 회귀 검사한다.
- 학생증을 제출하지 않은 계정은 관리자 '심사 대기' 목록·숫자에서 제외한다. 제출 없는 승인은 UI와 DB 모두 차단한다.
- 관리자 승인 취소 시 공개 모집 목록에서 즉시 제외하고 새로운 매칭 신청·수락을 차단한다.
- 신규 API는 로그인·DB 소유권·활성 상태를 확인한다. 사용자 수정 가능한 Auth metadata로 권한을 판단하지 않는다.

변경 SQL 전체: ../supabase/migrations/20261011230431_deferred_student_verification.sql.
CLI가 생성한 버전은 UTC 기준이며 한국 시간으로 2026-10-12 생성이다.

baseline.sql, 테스트 SQL, 테스트용 Auth/Storage 초기화 스크립트는 운영에 실행하지 않는다.
새 테이블 외 기존 테이블 컬럼·제약조건·UUID·기존 회원 데이터의 일괄 변경은 없다.

기존 Auth 설정·Provider·환경변수·프로젝트 요금·Storage 버킷 설정을 변경하지 않는다.

- 로컬 브라우저에서는 API 응답을 가상 데이터로 고정해 가입·초안 수정·승인 후 공개·사진 제출·기존 관리 화면·4개 언어를 검사한다.
- 최초 브라우저 실행의 문구 기대값과 테스트용 이메일을 수정했다. 중간 빌드와 미리보기의 dist 공유로 발생한 테스트 환경 충돌을 제거하고 최종 실행은 단독으로 수행한다.

## 적용 순서 및 중단 조건

1. 사용자의 운영 적용 승인을 받는다. GitHub main push/merge와 운영 SQL 실행은 아직 수행하지 않는다.
2. 변경 SQL·커밋을 확정하고 현재 배포 ID와 DB 복구 가능한 백업 시점을 확인한다.
   백업 여부와 복구 가능 시간을 실제로 확인할 수 없으면 적용하지 않는다.
   사전 함수·정책 정의 스냅샷은 복구 참고자료이며 데이터 백업을 대신하지 않는다.
3. 읽기 전용 사전 검사를 반복한다. 예상 밖 함수 변경, 같은 이름의 초안 테이블/함수,
   승인 상태 불일치, 중복 진행 팀이 발견되면 변경 내용을 재검토할 때까지 중단한다.
4. migration을 BEGIN/COMMIT으로 감싸 적용한다. lock_timeout 5초, statement_timeout 30초를 유지한다.
   테이블 재작성·기존 데이터 backfill이 없어 계획된 서비스 중단은 없다.
   함수/트리거 교체에는 짧은 DDL 잠금이 발생할 수 있으며 무중단을 보장하지 않는다.
   잠금이나 SQL 오류가 나면 전체 롤백하고 프런트엔드 전환을 하지 않는다.
5. DB 정책·함수·권한 및 PostgREST schema cache 갱신을 확인한다.
   기존 클라이언트가 호환되므로 DB 변경 후 프런트엔드를 전환한다.
6. 동일한 운영 환경변수로 새 프런트엔드를 배포한다. 브랜치 미리보기 검증 후 운영 전환한다.
   업로드·승인·공개를 운영에서 검증할 테스트 계정 및 범위는 사전에 사용자와 정한다.
7. 기존 로그인, 승인 회원 팀 수정, 홈 남녀 관리자 보기, 매칭·알림, 승인 전 제한,
   심사 목록을 확인하고 오류율·응답 지연·RLS/Storage 거부 오류를 확인한다.
   실제 회원 연락처가 노출되거나 승인 전 공개/매칭이 가능하면 즉시 배포를 되돌린다.

## 복구

- SQL 트랜잭션 실패: 전체 롤백. 새 UI를 배포하지 않는다.
- SQL 성공 후 새 UI 실패: 기록한 기존 프런트엔드 배포로 되돌린다.
  기존 사진 포함 가입과 승인 회원의 공개 팀·매칭 경로는 새 DB에서도 회귀 검사를 통과했다.
- 되돌리는 동안 새 흐름으로 가입한 미제출 회원과 초안은 보존한다.
  이전 UI에는 나중에 제출하는 화면이 없으므로 이 회원의 학생증 제출·초안 공개는 수정 배포 전까지 불편할 수 있다.
  문제 발생 시 빠르게 새 인증 화면을 복구하는 수정 배포를 우선한다.
- 운영 초안 테이블을 DROP하거나 새 회원을 삭제하는 방식으로 되돌리지 않는다.
  기존 공개 팀·회원·Auth·학생증 파일은 이 기능의 롤백 대상으로 삭제하지 않는다.
- 잘못된 데이터 변경이 별도로 발생한 경우 사용자 영향과 복구 범위를 보고하고 확인한 백업 복구 절차를 따른다.

참고: Supabase RLS 공식 문서 https://supabase.com/docs/guides/database/postgres/row-level-security.
