# 춘천과팅

강원대 · 한림대 · 성심대 · 춘교대 학생을 위한 1:1~4:4 과팅 매칭 웹앱입니다.
React 18, TypeScript, Vite, Tailwind CSS와 Supabase(Auth/Postgres/Storage)를 사용하며 Vercel로 배포합니다.

## 로컬 실행

Node.js 22.12 이상 23 미만을 사용합니다.

```sh
npm ci
cp .env.example .env.local
# .env.local에 프로젝트 URL과 공개용 anon/publishable 키 입력
npm run dev
```

브라우저 환경변수는 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` 두 개입니다. `service_role` JWT와 `sb_secret_` 키는 사용할 수 없습니다. 실제 키·환경파일·학생증·회원 데이터는 저장소에 넣지 않습니다.

## 검증

```sh
npm run check                  # 타입 검사, 컴포넌트/API 테스트, 프로덕션 빌드
npm audit --audit-level=moderate
npm run test:db                # 로컬 PostgreSQL 17 필요
npm run test:e2e               # 로컬 Chrome 필요
npm run test:db:resilience     # 별도 DB 복원·동시 부하 검사
npm run test:integration:local # Docker에서 실제 Auth·Storage·MFA 전체 흐름
```

DB 검증은 임시 PostgreSQL 인스턴스를 만들고 합성 데이터만 사용합니다. 운영 DB 접속 정보가 필요하지 않습니다. 기존 취약점 재현과 수정 후 권한·가입·재동의·팀 저장 원자성·매칭 동시성·탈퇴 정리를 검증합니다. 자세한 설명은 [DB 테스트 안내](supabase/tests/README.md)에 있습니다.

브라우저 테스트는 별도 로컬 빌드에서 모바일 화면, 로그인, 가입 복구, 관리자 접근 차단, 오류 후 재시도를 확인합니다. 모든 백엔드 응답은 가짜 데이터이며 실제 Supabase 요청은 차단합니다. CI에서는 Playwright Chromium을 설치해 사용합니다. 실제 Vercel 보안 헤더와 운영 Auth/Storage 설정은 배포 후 별도로 확인해야 합니다.

GitHub Actions는 애플리케이션 검사, 의존성 취약점 검사, 브라우저 테스트, PostgreSQL 17 회귀 테스트를 실행합니다. Keepalive 작업은 개인정보를 읽지 않는 공개 통계 RPC만 호출합니다.

초기 자바스크립트의 정적 의존성까지 합한 gzip 용량이 180 KiB를 넘으면 빌드를 중단합니다. 한국어 외 번역과 관리자 2단계 인증 화면은 필요할 때 불러옵니다. 복원·부하·실제 Supabase 검사 범위와 재실행 방법은 [검증 증거](docs/validation/README.md)에 있습니다. 로컬 성능 측정은 운영 서버의 처리량이나 복구시간 보장을 뜻하지 않습니다.

배포 후에는 [운영 배포 검증](docs/production-verification.md)에 따라 정확한 배포 커밋과 실제 공개 화면·권한을 읽기 전용으로 확인합니다.

## 운영 DB 변경과 배포

**운영 프로젝트에 `supabase/baseline.sql`을 적용하지 마세요.** 이 파일은 독립 테스트 DB 재현용 스키마입니다. 운영 변경은 `supabase/migrations/`의 검토된 증분 변경만 적용합니다.

기존 서비스의 DB 프로젝트 이름은 `chuncheon-dating4.0`이며 5.0 화면과 연결되어 있습니다. 프로젝트 식별과 적용 순서, 호환성, 복구 방법은 [DB 배포 안내](supabase/README.md)를 따릅니다.

1. 로컬 및 CI 검증을 완료합니다.
2. 운영 DB의 중복 활성 팀, 테이블·상태·파일 수를 확인합니다.
3. 권한 보강과 신규 RPC를 하나의 트랜잭션으로 먼저 적용합니다. 기존 클라이언트 API는 유지합니다.
4. Vercel 환경변수 두 개를 유지하고 검증된 프론트엔드를 배포합니다.
5. 실제 주소에서 공개 화면·직접 경로 접근·보안 헤더·공개 통계·익명 데이터 접근 차단을 확인합니다.
6. 완료된 탈퇴 기록의 남은 개인정보 정리는 별도 마이그레이션으로 적용하고 레코드 수가 보존되는지 확인합니다.

프론트엔드에 문제가 생기면 이전 배포로 되돌릴 수 있습니다. 이때 DB의 보안 수정을 되돌리거나 baseline을 복원하지 않습니다. 특정 정책의 호환성 문제는 좁은 범위의 후속 수정으로 해결합니다. 이미 완료된 탈퇴자의 개인정보 정리는 복원하지 않습니다.

## 주요 데이터 경계

- 가입 시 관리자 권한·인증 완료 상태를 임의로 지정할 수 없습니다.
- 공개 팀 정보에는 전체 학번과 연락처가 포함되지 않습니다. 연락처는 본인 팀과 관리자에게만 보이며, 매칭 후에도 상대에게 직접 공개하지 않는 기존 방식을 유지합니다.
- 팀과 팀원은 `save_my_team`으로 함께 저장하여 오류 시 전체 변경을 취소합니다.
- 동일 팀에 대한 동시 수락은 DB에서 직렬화하며 활성/매칭 팀은 소유자별 하나로 제한합니다.
- 학생증은 비공개 버킷에 저장하며 업로드는 5 MiB 이하의 허용된 이미지 형식으로 제한합니다.
- 관리자 탈퇴 처리 시 먼저 서버에서 대상 권한을 확인하고 학생증 파일을 정리합니다. DB는 남아 있는 파일이 있으면 최종 처리를 거절합니다.
- 인증 상태와 프로필 조회를 분리합니다. 조회 실패는 빈 목록이나 로그아웃으로 숨기지 않고 복구 경로를 제공합니다.
- 활성 관리자는 홈에서 남녀 팀을 모두 보고 성별로 좁힐 수 있습니다. 일반 회원의 상대 성별 조회와 신청 규칙은 유지합니다.
- 관리자는 `/admin/security`에서 본인의 인증 앱을 등록할 수 있습니다. 등록 완료 후에는 DB·파일·관리자 요청과 화면 모두 2단계 인증을 요구합니다. 미완료 등록은 기존 접근을 막지 않습니다.

## 운영 메모

- 약관 버전은 현재 `v5.1`입니다. 변경할 때 `src/lib/terms.ts`와 DB의 재동의 허용 버전을 함께 갱신해야 합니다.
- 사용자 알림 발송과 비밀번호 재설정 지원은 관리자 수동 업무입니다. 자동 발송 서비스는 포함하지 않습니다.
- 탈퇴 처리는 서비스 데이터 익명화이며 Auth 계정 자체의 완전 삭제는 아닙니다. 삭제된 프로필은 서비스 이용과 업로드를 차단합니다.
- 유출 비밀번호 차단은 Supabase Auth 설정과 요금제에서 별도로 확인해야 합니다.
- 테스트는 실제 회원의 계정으로 가입·매칭·파일 삭제를 실행하지 않습니다. 운영 변경 후에도 오류 로그와 회원 문의를 확인해야 합니다.
- 관리자 인증 등록, 운영 백업, 개인정보 보관 정책의 완료 기준은 [운영 체크리스트](docs/operations-checklist.md)를 따릅니다.
